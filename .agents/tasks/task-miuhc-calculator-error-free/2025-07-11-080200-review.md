# MiUHC premium calculator: data lookup hardening and Smart plan gating

The calculator performed matrix lookups against `miuhc-premi.js` using numeric age keys, but the data file stores ages as string keys (`"0"`, `"30"`, etc.), causing every lookup to silently return `undefined`. The `|| 0` fallback then masked the failure by showing "Rp 0" instead of surfacing an error. This change fixes the type mismatch, adds explicit validation for every lookup, gates Smart plan toggles to match actual data availability (Sapphire Smart absent from both products; Jade/Jade ID Smart absent from Syariah), and provides user-facing fallback messages when a plan/age/gender combination has no data.

**Watch for:** The `noSmartPlans` list is duplicated in three places (confirmed) — `buildPlanGrid`, `updateSmartAvailability`, and the product-switch handler — creating a maintenance trap if plan availability changes. One secondary concern: the age key type mismatch fix relies on `String(usia)` at every call site rather than coercing once at assignment (possible inconsistency risk if a new lookup is added without `String()`).

## High-level view

The root cause was a type mismatch: `curUsia` held a number, the JSON keys are strings. Every `DATA[cat]?.[gender]?.[usia]?.[plan]` resolved to `undefined`, and `|| 0` turned that into a silent zero. The fix applies `String(usia)` at each lookup and replaces the `|| 0` pattern with explicit `typeof === 'number' && > 0 && isFinite()` guards, so missing data now triggers a visible "Plan tidak tersedia" message rather than a misleading zero premium.

Smart plan availability is gated against the actual data — the toggle disables for combinations without data and resets state on product switch. The "which plans lack Smart" knowledge is hardcoded in three separate arrays that must stay in sync manually; a single source-of-truth constant or a runtime check against the data keys would be more resilient.

1. **Triplicated noSmartPlans arrays** — The same plan-availability list appears in `buildPlanGrid`, `updateSmartAvailability`, and the product-switch event handler. Extract to a single function or constant to prevent drift.
2. **String coercion at every call site** — `String(usia)` is repeated in 5 lookup expressions. If `curUsia` were stored as a string (or coerced once in `setUsia`), every downstream lookup would be safe by construction. Currently, adding a new lookup without `String()` would silently reintroduce the original bug.
3. **innerHTML injection in fallback message** — `resultEmpty.innerHTML` is set with a template literal. The content is static here, but the pattern invites future XSS if dynamic values are interpolated later. Consider `textContent` with a prepended emoji element.
4. **Rider toggle state asymmetry on product switch** — When switching from Syariah to Konvensional, `curGigi` is reset and the checkbox unchecked, but `curJalan` is not re-validated against the new product's data. The current data has full Jalan coverage for both products so this isn't a live bug, but the asymmetry means a future data gap in Jalan would fail open (rider added at zero with no feedback).

## Type mismatch fix and validation strategy

The original code passed `curUsia` (a number) directly into `DATA[inapCat]?.[curGender]?.[usia]?.[planKey]`. Since `miuhc-premi.js` keys ages as strings (`"0"` through `"85"`), every lookup returned `undefined`. The fix applies `String(usia)` at each of the five lookup sites. This is correct but fragile: a developer adding a sixth lookup must remember the coercion. Storing `curUsia` as a string or coercing once in `setUsia` would make the contract structural rather than relying on per-call-site discipline.

## Smart plan gating and state reset

The data confirms (verified via key inspection):
- `konv_inap` age 0: keys include `Jade Smart` and `Jade ID Smart` but **not** `Sapphire Smart`
- `sya_inap` age 0: keys include neither `Jade Smart`, `Jade ID Smart`, nor `Sapphire Smart`
- `sya_jalan` and `sya_gigi`: same as `sya_inap` — no Jade/Jade ID/Sapphire Smart

The `noSmartPlans` array logic appears in three places with slightly different forms:

```javascript
// In buildPlanGrid (uses " Smart" suffix on plan names):
const noSmart = curProduk === 'sya'
  ? ['Jade Smart', 'Jade ID Smart', 'Sapphire Smart']
  : ['Sapphire Smart'];

// In updateSmartAvailability (base plan names):
const noSmartPlans = curProduk === 'sya'
  ? ['Jade', 'Jade ID', 'Sapphire']
  : ['Sapphire'];

// In product switch handler (identical to above):
const noSmartPlans = curProduk === 'sya'
  ? ['Jade', 'Jade ID', 'Sapphire']
  : ['Sapphire'];
```

If the data file is regenerated with different plan availability (e.g., Sapphire Smart added to konv), all three must be updated independently. A single `getNoSmartPlans(produk)` function would eliminate drift risk.

## Fallback message injection pattern

The `recalc` fallback uses `resultEmpty.innerHTML` with a template literal containing a static string. The rest of the file uses `textContent` for dynamic values. If someone later interpolates user-controlled data (plan name, age) into that template, it becomes an injection vector. On a static site with no user-generated content this is low-severity, but switching to `textContent` would close the door entirely.
